我有个脚本，在起新 worker 之前先判断旧的那个还活着没有，活着就别重复拉起。判断逻辑很直白：按名字找进程，找到就跳过。测的时候好好的。可上线后它开始犯两种毛病——没有进程在跑的时候不肯拉起，有进程在跑的时候又拉起了重复的。两个方向都错，出自同一行代码。

那行大致是 `pgrep -f my_worker.py`。这个坑很老，但看破一次就再也绕不过去：进程表里不只有我的 worker，还有一瞬间躺着我这条“用来找 worker”的命令本身——而这条命令的参数里，明晃晃写着 `my_worker.py`。于是搜索找到了它自己。`pgrep -f` 匹配的是整条命令行，而这个检查动作的整条命令行，本身就是一句“提到了被检查对象”的话。

## 观察者站进了被观察的画面里

代码上是很小的错，道理上是很大的错。我用来测“它在不在跑”的那把尺子，尺子自己身上就刻着我要扫的那个标签。这是进程管理版的“称重时秤把自己也一起称进去了”，或者“问卷把发问卷的人也算成了一名受访者”。工具并不站在它检查的系统之外，它站在画面里，举着一块写着搜索词的牌子。

这也解释了为什么错误会往两个相反方向发生、看着自相矛盾。真 worker 挂了的时候，检查依然找得到*一个*匹配——它自己那条 grep——于是判定“已经在跑”，跳过拉起。后来我改用 `pkill -f my_worker.py` 去清理残留，那个 pattern 同样匹配到 `pkill` 命令自己那条命令行，某些执行顺序下，工具本身就成了要被杀的候选。这件事最壮烈的版本是：`pkill -f` 反手把自己所在的那个 shell 给杀了，因为 shell 的命令串里含着这个 pattern。你本想清理一个 worker，结果剁了自己的手。

## 为什么测试抓不到

它能躲过测试，是因为这个“自我匹配”既依赖时序，又通常无害。多数时候真进程也在，检查返回“在跑”，恰好答对了——但答对的理由是错的。只要它跟现实一致，自我匹配就隐形。它只在一个时刻现形：正是你最需要这个检查既正确又独立的时候——真东西*不在*的时候。那正是幽灵匹配成为唯一匹配的场景，也正是你 happy-path 测试永远碰不到的场景，因为测试里你都是先起 worker、再去检查。

于是 bug 藏在“答案是对的”和“答案对是因为我量的就是它”这两句话中间的缝里。这俩不是一回事。一个碰巧正确的检查，会在条件一变的第一时间背叛你。

## 一般形态

把具体命令剥掉，这个模式在自动化里到处都是：**任何探针，只要它自身的身份里含着它要探测的那个特征，就会污染自己的读数。** 一个 grep “error” 的日志扫描器，把 “error” 这个词写进了它正在扫的那份日志。一个按 glob 列文件的清理任务，那个 glob 也匹配它自己产出的文件。一个统计打开连接数的监控，把它为了统计而打开的那条连接也算了进去。一个上报请求速率的健康端点，速率被健康检查本身抬高了。每一例里，观察这个动作都往被观察对象里注入了一个实例，计数于是刚好差一——差的那一个，就是你自己。

这个 off-by-one 就是破绽。当一个计数“永远比应该的多一个”、或者“怎么都到不了零”，就该怀疑：你把自己也数进去了。

## 怎么把自己从画面里挪出去

有几种诚实的修法，共同点是：让仪器和被测对象可区分。

按探针不可能碰巧穿在身上的东西去匹配。`pgrep` 不加 `-f` 匹配的是进程*名*而非整条命令行，于是你的 `pgrep`（名字叫 `pgrep`）不会匹配到一个名叫 `python` 的 worker。更好的做法是匹配一个 worker 拥有、而检查者永远不会拥有的稳定身份——启动时写进 lockfile 的 PID、一个监听端口、一个具名 socket。一个去问“*这个具体 PID* 还活着吗”“*这个端口* 被绑了吗”的检查，根本没办法用自己的倒影来作答。

如果非得扫命令行，就显式把自己排除掉。滤掉自己的 PID（`$$`），或者把 pattern 写成匹配不到匹配器自己的样子——那个老把戏：搜 `[m]y_worker` 而不是 `my_worker`，方括号是个字符类，匹配 `m`，但你 grep 参数里那串字面量 `[m]y_worker` 并不满足这个正则，所以 grep 永远找不到它自己。丑，但丑得有意为之：它把“我不属于我要找的那类东西”这句话，直接编码进了 pattern 里。

至于那个有破坏性的版本，绝不要在没证明目标不是自己之前，就让 kill-by-pattern 跑起来。先解析成一个具体 PID，确认它不是 `$$`、不是自己的祖先进程，然后才动手。省掉这一步的代价不是一个错误的数字——是把那个本该执行“杀”的进程给杀了。

## 教训底下的教训

窄的收获是：别用一个你 grep 自己也含着的字符串去 grep 进程。宽的那个，是关于一整类被测试奖励你去忽视的测量 bug。每当你造出一个“按 pattern 去检视系统”的东西，在信它的答案之前先问一句：*我“看”这个动作，会不会往我要找的东西里加进一个实例？* 如果会，那你的读数就含着观察者，而一个含着观察者的读数不是对系统的测量——它是对“系统加你”的测量，而你只会在某一天系统空了、画面里只剩你自己的时候，才第一次注意到这个差别。
