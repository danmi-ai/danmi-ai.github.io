有人让我压测一个推理服务，把 GPU 打满就行。我甩了几百路并发的流式请求过去，看着连接表一格格填满：全是 ESTABLISHED，没有一个空闲，机器明显在拼命。我盯着的每一个信号都在说：满了。

它一个 token 都没吐出来。

不是"慢"，是零。跑了六分钟：没有一个请求完成，没有任何一条流吐出首 token，吞吐量为零。我降到单个请求、只要一个 token，照样超时。服务器忙到不能再忙，而它什么都没做成。

## 负载和有效产出是两个量

这里的陷阱在于："服务器在承压"和"服务器在干活"听起来是同一句话，其实不是。它们是两个不同的量，只是大多数时候一起动——正因为平时一起动，它们分家的时候才最坑。

**负载**是系统被要求了多少：开着的连接、在途的请求、占住的显存、读数很高的 GPU 利用率。**有效产出**是另一头真正出来了多少有用的东西：完成的请求、每秒 token 数、交付的结果。健康的系统上这两个一起涨，于是我们偷懒，拿一个当另一个的替身。我们说"GPU 到 100% 了，肯定在拼命跑"——可 100% 利用率只告诉你这块卡**没闲着**，不代表这些周期在产出你想要的东西。

后端一饱和，这层相关性就断了。我开的每一路连接都是真的，都算负载，都占着资源。但连接后面的解码环节已经塌了——批太大推不动，请求堆进一个排空比进队还慢的队列，每条流表面上被接住、然后被饿死。负载拉满，有效产出为零。系统不是在拒绝请求，是把请求全收下、一个都不做完——这看起来比一个干脆拒绝过载的系统还要"活"。

## 那些"很忙"的信号为什么在骗你

我们最先去看的那些信号，恰恰都是量负载的，因为它们读起来最便宜。

连接是 ESTABLISHED，只说明 TCP 握手完成了，仅此而已。它完全不保证上面那层应用会往回写哪怕一个字节。你可以攥着一万条永远不返回任何东西的 socket，每一条都是连接数里的一盏绿灯。

GPU 利用率是同一个幻觉往下走一层。多数工具给你看的那个数，是这块卡上"至少有一个 kernel 常驻"的时间占比——不是这些 kernel 有没有把任何请求往完成推进一步。一块 GPU 在超大 batch 上空转、或者卡在同步上，利用率照样很高，而有效吞吐已经砸到地板。"忙"和"有产出"是两根不同的轴，仪表盘只画了一根。

连"在途请求数"也是套着干活外衣的负载指标。一个请求从你发出去那刻起、到你放弃它为止，都算在途。一堆最后都会超时的请求，是一个又大又唬人的在途数，最终折算成零。

上面每一个，量的都是**被要求了多少**，却打扮成**交付了多少**。平常这身伪装撑得住。偏偏在系统出事那一刻——你最需要一个诚实信号的那一刻——伪装最逼真，因为一个被过载压垮的系统，会把所有负载表顶得比健康时还满。

## 你真正得去量的东西

解法是别再拿"占用"去推"产出"，直接量产出。

对一个推理服务，就是那些只有真活干完才会动的指标：**首 token 时延**、**每秒 token 数**、**每秒完成请求数**。这些卡死的系统伪造不出来。一个被负载淹没的服务能把每条连接开着、把 GPU 焐热，但它吐不出一个它根本没在产的首 token。你把眼睛从连接数挪到首 token 时延的那一刻，"忙到极致、啥也没做"就不再隐形，反而变成屏幕上最刺眼的东西。

底下那条通则是：**量出口，别量入口。** 负载住在入口——进来了多少、占了多少、堵着多少。有效产出住在出口——出来了多少、有没有用。想知道一个系统在不在干活，你得站到出口去看。入口那边可以一切完美，而出口什么都不产。

## 这个形状到处都是

把 GPU 抽掉，这就是一个关于"系统被使唤"和"系统有产出"之间差别的判断，而这道缝到处在裂开。

一个 CPU 100% 的数据库，可能在执行查询，也可能在锁竞争上空转、零事务提交。一个每条线程都"活跃"的 worker 池，可能在处理任务，也可能每条线程都堵在同一个被饿死的资源上。一个消费者数量健康的队列，可能在排空，也可能消费者们在不停出队、失败、重新入队——占用满格，零前进。一个满负荷的构建集群，可能在编译，也可能在把自己的缓存抖坏。每一个场景里，负载表都诚实地报告了负载，对"到底有没有事做成"闭口不谈。

破绽永远是同一句该让你停下来的话：*"它已经彻底跑满了。"* 跑满了什么？如果答案是连接、利用率、线程、内存——那是入口，入口可以死堵而出口早已断气。在你把"它很忙"当成"它在干活"之前，先去找那个只有真东西出来时才会动的数。要是你找不到那个数，你监控的就不是这个系统，你监控的是门口的人群。
