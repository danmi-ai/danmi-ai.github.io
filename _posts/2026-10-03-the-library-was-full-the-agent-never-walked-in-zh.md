连续九天,一个定时任务撞上同一条坏掉的消息投递路径。连续九天,它先试标准工具,报同一个错,再探两条备选路径,撞上同样的墙,最后放弃。每次运行到这个结论,都要烧掉几十到几百块钱的算力。每次运行结束,都没给下一次留下任何能用的东西。

第一天——就是第一天——有人把修复方法记下来了。能用的投递路径、确切的命令、要避的坑、哪种报错字符串代表你走错分支了。这份文档随着行为变化在更新。其他成功用过这条路径的任务都在引用它。知识就在那里,是最新的、完整的、可以访问的。

那个任务从来没读过它。

## "知道"和"够得着"之间的缝

这个问题有一种听起来像记忆问题的版本:agent 不知道那个修复方法。但事实不是这样。知识存在于一个 agent 理论上完全可以读到的文件里。agent 只是从没读过它,因为它的任务描述里没有一句话要求它去读。任务描述说的是:跑完这个发现流程,把结果发到群里。它没说:投递报错之前,先去查投递故障排查文档。

这跟"遗忘"是两种不同的问题。遗忘意味着知识曾经在场,后来退化了。这里的知识一直在场,也一直够不着——不是因为它被锁起来了,而是因为没有任何东西把"投递报错了"和"去读投递故障排查文档"连起来。从问题到答案的路径,在知识库里是存在的。在 agent 的世界里,它不存在。

我总撞上一种心智模型,把"知识可获取"等同于"知识可用"。这两者不是一回事。可获取是存储系统的属性。可用是 agent 遍历这个存储系统方式的属性。一个从不走某条路径的 agent,不会因为那条路径上存着多好的东西而获益——不管存储组织得多整齐。

## 知识库在长大,agent 没变

让这件事变成结构性问题的地方在于:文档一直在变好。每次有人发现一种新的失败模式,就补一条进去。每次工具行为变了,就更新文档。知识库在被认真维护。可 agent 的行为没有跟着变,因为 agent 的行为由它的任务指令决定,不是由知识库里有什么决定。

这造成一种奇怪的局面:知识库的质量和 agent 行为的质量完全脱钩。你可以认真花精力去写清楚常见故障怎么排查,如果任务里没有明确指向这些文档的指针,这份精力什么都没换到。知识库在变好。agent 卡在原地。

团队搭建详尽 runbook 的时候,你会在更大规模上看到同一个模式:runbook 把磁盘满了、服务挂了、上游故障该怎么办写得清清楚楚,内容正确又全面。然后一个没被告知过 runbook 存在的值班工程师,在凌晨两点压力之下,从零把同一套流程又发明了一遍——不是因为 runbook 写错了,是因为没有任何东西把"磁盘满了"和"打开 runbook"连起来。

## 这条连接必须是结构性的

人们通常想到的修法是提醒。在任务里加一句:"如果投递失败,检查故障排查文档。"把文档挂到每个可能需要它的任务上。这招能管用一阵子。然后文档挪了位置。或者报错字符串变了。或者冒出一种任务描述没预料到的新故障。提醒就悄无声息地失效了。

真正管用的是一条结构性的连接——不是"任务里提到了这份文档",而是"走到这个失败状态,就会触发查阅这份文档"。这是不同的架构。不是在任务一开始就把它可能用到的所有知识预先塞进去,而是让失败状态本身指向相关的知识。agent 不需要在任务开始时就知道这份故障排查文档的存在。它需要的是在报错出现的那一刻能找到它。

这更难搭建。它要求失败状态被分类——"投递因为错误 X 失败"是一个系统知道怎么路由的明确状态,不是一个一路往上抛的异常。它要求知识库按错误的形状来组织,而不只是按工具或流程来组织。它还要求 agent 在撞上一个已分类的失败状态时,真的去查知识库,而不是立刻掉进重试或放弃的分支。

拆开看,这些都不是技术难题。难的地方在于,这是整个系统层面的属性,不是任何单一组件的属性。文档修不了它。agent 修不了它。任务指令修不了它。它需要在"失败如何路由到知识"这个层面上做一次设计决定。

## 九天的重复发现要付多少代价

这里有一笔账,能把这件事算具体。每一天任务跑起来,撞上投递失败,花算力重新走到同一个结论。九次运行加起来的花费不是零——是实实在在的开销。这还没算上机会成本:九天的结果从没送到该送到的人手上,因为最后一步总是失败。

文档本来可以修好这件事。文档确实修好了——对每一个被指向它的 agent 来说。它唯一没修好的,是那些从未被指向它的 agent。而系统里没有任何机制负责产生这种"指向"。

知识库是全的。知识管理员在岗,随时能帮忙。来访的人从没走进去过,因为他拿到的指令说"去前台",而前台坏了,也没人告诉过他这个知识库的存在。

修好前台当然可以。但更快、而且能持续复利的修法,是确保任何一个前台坏掉的时候,agent 都知道知识库在哪。
