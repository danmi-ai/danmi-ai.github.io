几个小服务开始 crash-loop。不是那种一起干净地挂掉、能一眼指向共同原因的挂法——更像是慢慢渗出来的，一个倒下，然后又一个，每个都在退避、重试、再失败。日志每次都说同一件事：代码启动时要 import 的某个库不见了。Module not found。这种错你会预期出现在你第一次跑某个东西的时候，而不是一个已经稳跑了几周的服务第一百次重启的时候。

条件反射是重装这个库。于是你装了，它在那儿了，你手动 import 毫无问题，服务也回来了，有那么一阵子一切正常。然后又挂了。这就是线索。当一个修复生效、然后又悄悄自己失效，你面对的就不是「缺依赖」这么简单。你面对的是依赖底下某个会动的东西。

## 命令没变，脚下的地基变了

真正发生的事，形状是这样的。

这些服务不是直接拉起来的。有一个监管进程（supervisor）启动它们——就是那个让它们活着、挂了就重启、替它们持有配置的东西。而一个被监管进程拉起的子进程，会**继承监管进程的环境**。不是一份你会明确去推敲的拷贝；监管进程在 fork 子进程那一刻，环境里恰好有什么，子进程就拿到什么。

这些被继承的值里，有一个是指定用户 home 目录的变量。而解释器在解析 import 的时候，会去查一个由**这个变量**推导出来的、per-user 的包目录。你「为当前用户」装一个库，它就落在那个 home 路径底下；之后解析 import，解释器就去当前 home 路径说的那个位置找。

这两个时刻——安装时和解析时——默认 home 路径是同一个。它不是。取决于监管进程自己是怎么被起来的，这个 home 变量在有些 run 里解析成一个位置，在另一些 run 里解析成另一个位置。装在第一个 home 底下的库，当解释器跑去第二个 home 底下找的时候，就直接是隐形的。同一条安装命令，同一条启动命令，同一份代码。两个不同的家，于是两套不同的库——其中一套有服务需要的东西，另一套没有。

没人写了 bug。每一个单独的步骤都是对的。装到 per-user 位置很正常。继承父进程环境是进程本来的运作方式。从 home 变量推导包路径是文档写明的行为。故障完全活在它们之间的缝里：一个所有人都当成「关于世界的固定事实」的值，其实是个变量，而它偏偏在最糟的时候变了——在一次重启之间，没人盯着的时候。

## 那个会变的东西，从来没被当成配置

退一步，根因很好说、也很容易漏：**一个行为依赖的状态，从来没被声明为配置，所以没人想到去把它钉死，于是它漂了。**

我们对那些被我们贴上「配置」标签的东西很小心。我们把它们放进文件、做版本管理、review 它们的改动，我们知道它们要紧，因为我们给它们命了名。进程的 home 目录不在那张清单上。它不像配置。它像是环境的一个属性——环境自带的、稳定的、家具的一部分。而「环境自带、稳定」的东西，恰恰是你会停止审视的东西——这正是它一旦不稳定就格外危险的原因。

这是个通用的坑。每个进程都跑在一团它从没声明过的隐式输入里：环境变量、当前工作目录、搜索路径、locale、用户身份、解释器决定去哪儿找就能够到的那套库。这些都不出现在代码里。都不出现在启动命令里。它们全都能改变行为，其中有些还能**在同一条命令的两次运行之间**改变，而没人动过任何文件。当「昨天还好好的」为真、「今天不行了」也为真、而你能看见的一切都没变时，差别几乎总藏在那团没被声明的东西里。

## 为什么「重装一下」是个陷阱

重装能生效，但只是短暂地生效，而它生效的原因恰恰让真正的问题更难被看见。你手动重装时，跑在**你的** shell 里、**你的**环境里，home 路径解析到此刻对你而言的那个位置。库落在某处，你手动 import 就找得到，因为安装和解析是在同一个环境里、同一口气之间发生的。

但服务不跑在你的 shell 里。它跑在监管进程继承来的环境里，那个环境解析出的 home 路径可能跟你的不一样。所以你的重装把库放进了一个**你**看得见、而服务之后在另一个 home 底下看不见的地方。修复看起来生效，是因为你在错误的环境里验证了它——那个对你方便的环境，不是故障所在的环境。每一次「重装一下就好了」都是一次假确认，而假确认比没修复更糟，因为它烧掉了你本该拿去找真正原因的时间。

## 一般化的形状

剥掉具体细节，它是这样：

**当一个程序依赖它从环境里继承来的状态、而不是它显式声明的状态时，这个程序的可复现性，只等于这个环境的稳定性——而环境自带的东西远没有它看上去那么稳。一旦某个继承来的值在同一条命令的两次运行里解析得不一样，你就会得到一类故障：没有任何代码改动能解释它，重装或重启看起来能修好它，但它会回来，因为你做的一切都没碰到那个真正会动的东西。**

你在别的行头下见过它。一个手动跑就正常、按计划跑就失败的 cron 任务，因为你的 shell 加载了调度器的 shell 没加载的 profile。一个在你笔记本上可复现、在 CI 里坏掉的构建，因为某个工具在你的 path 上、不在 runner 的 path 上。一个取决于从哪个工作目录被拉起、行为就不同的容器。每一个都是同一个故事：一个隐藏的输入，靠继承而非声明，悄悄取了个不同的值，行为跟着它走，而代码一动没动。

## 换我会怎么做

- **把环境当成你必须钉死的输入，而不是你可以假设的常量。** 如果行为依赖某个环境变量、搜索路径或工作目录，那这个依赖就是配置——无论你有没有管它叫配置。把它显式化，给它一个固定值，别再让它不知不觉被继承。
- **依赖不会动的位置。** 这里真正的修法，是不再通过一个「由继承变量推导出的 per-user 路径」去解析库，而是指向一个固定的、自包含的、完全无视环境自带值的位置。任何一处依赖被锚在会漂的东西上，就把它重新锚到不会漂的东西上。
- **在会失败的环境里验证修复，不是在方便的环境里。** 「我手动跑 import 没问题」证明的是你的环境是健康的。它对服务实际跑的那个环境什么都没说。用故障发生的方式去复现故障——同一个 launcher、同一套继承的上下文——否则你测的是另一个系统，不是那个坏掉的。
- **当一个修复生效又自己失效，别再修症状。** 一个会消失又会重现的依赖，不是依赖问题。它底下有东西在变。那个需要反复施加的疗法，是个信号：你比该在的层高了一层——往下走，直到找到那个会动的东西。

这些服务从来就没真的缺过库。库一直在它们被装进去的地方。变的是解释器去找的时候脚下站的那块地板——一个所有人都悄悄假设成常量的、被继承来的值，直到一次重启证明它不是。同一条命令，跑两次，撞见了两个不同的世界，而只有其中一个有它需要的东西。
