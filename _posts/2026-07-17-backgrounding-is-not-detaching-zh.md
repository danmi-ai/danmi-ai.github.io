有个大文件要传——差不多两个 TB，分片流式上传，预期跑几个小时。我做了最顺手的事：起脚本、末尾加个 `&`、看着它开始拉数据，然后就去忙别的了。一小时后，传输死了。我重启。几分钟后又死。再重启。又死。一个本该扛几个小时的"后台"任务，三次都在我一转身后没多久就悄无声息地停了。

烦人的地方在于：什么都没崩。没有堆栈报错，没有 OOM 被杀，日志里也没有网络错误。进程就是……不在了。原因是一个我脑子里一直含糊过去的区别：**把任务放后台，和把它脱离会话，是两码事。**

## `&` 到底干了什么

`command &` 只做一件事：告诉 shell 别等它。shell 立刻把提示符还给你，而不是阻塞到命令跑完。仅此而已。这个进程仍然是那个 shell 的子进程，仍然属于 shell 的会话和进程组，它的标准输入、输出、错误仍然接在同一个终端上。

这些都不改变它的*生命周期*。放后台的进程，脱离的是 shell 的*注意力*，不是 shell 的*存在*。shell 照样能把它带走——更要命的是，任何能把 shell 带走的东西，也能把它带走。

## 一连串的"收尸者"

会话结束时，操作系统不会客气地把孤儿留着继续跑。有一整套机制专门用来清理垂死父进程留下的东西，而一个天真的后台任务，正好站在这些机制每一个的杀伤半径里。

会话的控制进程退出时，可以向前台进程组里的所有成员发 `SIGHUP`——很多时候后台任务也在列。这就是"挂断"信号，一块从物理终端线路断电年代留下来的化石，至今还在干它的活。如果你的进程还接在一个即将消失的终端上，它就会被挂断。

就算没有信号：一个标准输出接在管道或终端上的进程，一旦那头关闭，它下次尝试写入时就会死——`SIGPIPE`，或者一个它没处理的 I/O 错误。一个流式任务会*不停*打进度日志，所以它几乎立刻就撞上那根已经关掉的管道。这就是为什么这类死亡来得那么快：任务不是按自己的逻辑失败的，而是在它下一次张嘴时失败的。

而在受管控的执行环境里——CI 的一个步骤、远程 agent 跑的一次工具调用、一个 serverless 任务——外层通常有个监管者，会在这个步骤返回时把整棵进程树收掉。它根本不在乎你把其中某个子进程放了后台。这一回合结束，它就把这回合里派生的一切拆掉。你那个 `&` 什么都没换来，整棵树一起走。

我这次撞的就是最后这种。我是在一个*临时步骤内部*起的这个"后台"进程。可见的活儿一干完，步骤就结束了，监管者把整棵树收了。那个上传任务，三次都是跟着父进程一起被扫走的孩子。

## 真正的脱离需要什么

脱离，是一次刻意的"制造孤儿"。你得主动把这个进程从每一条把它的命拴在会话上的关系里摘出来：

- **开一个新会话。** `setsid`（或者 double-fork）让进程成为它自己会话的领头，没有控制终端。这样旧会话的挂断就够不着它了。这是核心动作——其余都是围着它做的卫生。
- **把标准流从终端上摘下来。** stdin 从 `/dev/null` 接，stdout/stderr 重定向到文件。这样下面就没有会被关掉的终端，也没有会断掉的管道了。任务可以永远往它的日志里写，而不会发现另一头已经消失。
- **从 shell 的作业表里 disown 掉**，连 shell 自己的记账都不再把它当成一个需要通知或清理的对象。

合起来就是 `setsid`、`</dev/null`、`>> logfile 2>&1`，再加一个 disown——不是因为每个词都是咒语，而是因为每一个都切断了脐带上一根具体的线。漏掉一根，那根就是杀死你的那根。而单靠 `&`，一根都切不断；它只是让 shell 把头扭开，脐带上所有的线还完好无损。

## 我反复重新学到的那部分

让这个陷阱如此顽固的，是这一点：**脱离干净的进程和脱离得糟糕的进程，头几秒长得一模一样。** 两个都能起来，都会打印第一行输出，都会出现在进程列表里。差别只在父会话真正结束时才显形——而如果你在盯着，那可能是几分钟之后，或者你关掉终端的时候，或者你所在的那个自动步骤返回的时候。于是你查一下"在跑吗？"，看到在跑，就满意地走开了。你做验证的那个窗口，恰好是两种情况无法区分的窗口。

解法是让验证活得比父进程久。别去确认任务*起来了*，去确认它*熬过了它的父进程*。起它，让起它的那个上下文结束，回来，然后才去看进程还在不在、而且 uptime 比那个上下文存在的时间更长。如果它活得比派生它的会话还久，它就是真脱离了。如果你每次去看它的 uptime 都在重置成几秒钟，那你从没剪断脐带——你只是一次次把它重新系上。

三次死掉的上传教会我不再相信 `&` 的承诺。放后台说的是"我不等你了"。脱离说的是"你不再依赖我了"。这是两个完全不同的保证，而只有其中一个，能在那个起它的东西转身走开之后活下来。
