有人找我诊断一批 coding agent 的运行结果：分数全是零。不是低，是零，而且包括那些平台标记为「成功」的那些。

这个组合才是有意思的地方。一次运行状态是 `succeeded`、分数是 `0.0`，说明两套系统对「发生了什么」的判断不一致。而每次这种不一致，中间通常都夹着一个没人写下来的定义。

## 那些零分到底说了什么

任务本身正是 agent 应该擅长的那类：给你一个能跑但不能拆开看的程序，你从它的行为里推出规格，然后自己实现一份，并在固定路径下放一个构建脚本。评测方跑那个脚本，测出来的可执行文件。

每条失败记录的 reason 字符串一模一样：构建脚本不存在。不是「构建脚本执行失败」，不是「产物行为不对」，不是「第 7 个用例不匹配」。是不存在。二十多次运行，一个原因，零变化。

所以在碰模型之前我就知道这次失败长什么样。什么都没交出来。那些运行不管把时间花在哪了，反正没花在生成评测方要找的那个文件上。

## 先排掉几个无聊的可能

三项便宜的检查，按「跳过它我会有多丢脸」排序。

推理服务：agent loop 会用到的每条路径都健康——普通补全、tool call、流式、扩展思考、多轮 tool result。延迟正常，没有任何退化。

模型：同一个模型在另一套任务集上拿过满分。所以它做得了这类活。

这一批本身：大部分条目压根没跑。几百条被标为 skipped，全在同一秒内翻转，这是「被中断」的形态，不是一群各自失败的样本。这一点影响怎么读汇总数字——那些零分来自一小片实际跑过的切片，不是全集——但它没解释这片切片为什么什么都没产出。

连着三个「没问题」是个信号。基础设施健康、模型有能力，剩下的变量就是那条指令。

## 对照组只多了一段话

有一个几乎相同的任务族，同模型、同镜像、同 harness，拿到了 1.0。我 diff 了 prompt。

通过的那族，prompt 末尾多一小节讲交付纪律。大意是：开局第一件事，先把构建脚本和一个能编译的最小骨架建出来。探测要有节制。时间不够时，宁可交一个功能更少但能构建的版本，也不要交一个野心大但构建不起来的。

我抽了失败那批的 prompt。一条都没有。不是弱化版本——完全没有。

一段话，而且它跟领域无关。它没提要复刻的是什么程序，没提用什么语言，没提测试。它讲的只有一件事：**什么时候该停下来交东西**。1.0 和 0.0 之间的全部差别就是这个。

## 然后我用八轮复现了它

prompt diff 只是相关性，我不想把相关性当根因交出去。所以我在本地搭了个最小 agent loop——原始 prompt，一个 Bash 工具、一个 Write 工具、一个 Read 工具，一个会给出合理响应的脚本化假沙箱——然后看模型怎么用它的回合。

它一直在探测。装的是哪个编译器。哪个 Python。列目录。找参考二进制。不带参数跑一次，再带 help 跑一次，读 usage 文本。查版本。再列一次目录。

八轮，Write 调用零次。没有构建脚本，没有骨架，没有一行源码。它没有卡住、没有报错、没有拒绝——它在干活，而且看起来又勤奋又在行，干的是理解问题。而到了真实 harness 该没时间的那个点，磁盘上什么都没有。

这就闭环了。离线行为和线上一致，唯一驱动它的就是 prompt。

## 为什么「继续探索」在每一步都是理性选择

这部分值得留下来，因为它跟具体哪套任务集没关系。

想一下 agent 在任意一个回合的处境。它对一个必须复刻的程序只有部分信息。每一次探测都严格降低不确定性——多带一个 flag 跑一遍，它确实学到了东西。而写一个空壳构建脚本，它观察不到任何回报：没有新信息，没有可见奖励，而且感觉太早了——规格还没推完，谁会先写构建。

所以在每一个回合上，探测都优于提交。而且一路优到预算耗尽。那时候积累起来的理解——很可能相当不错——蒸发掉了，因为被打分的从来不是理解。

这条链上没有哪一步是错的。每一步都站得住。失败是全局的，在局部不可见，而这恰好是逐回合决策的策略看不见的那类失败。agent 的决策里没有「时钟是一种资源，交付不是免费的」这一项。除非外部给它装一个，它就会一路探索到灯灭。

## 镜像版本，以及两边共同缺的东西

我前段时间写过反过来的那种失败：用 RL 训的长程 agent 塌缩成盲目改代码——不读、不复现，直接改行，因为探索对最终奖励是不可见的。那个 agent 学会了跳过这个 agent 过度投入的一切。

同一套奖励结构，两种相反的病：

- 未训练的策略 + 开放式 prompt：无限探索，永不提交。
- 在稀疏终局奖励上训狠了的策略：立刻提交，从不探索。

两边都没有「什么时候该切换」的表示。一个把信息收集当免费，一个把它当没价值。这个行为的健康版本是一次相变——先侦察，直到边际信息量低于「还没交付」的代价，然后开建，有余量再打磨——而朴素的 prompt 和朴素的奖励里，都不存在能产生这次相变的压力。

所以一段「交付纪律」能把分数从 0 抬到 1。它不是领域知识，它是外部塞进去的预算策略，手工装的，因为 agent 自己不带。

## 那个状态字段是靠省略在撒谎

同一件事里的另一课。平台给什么都没交的运行报了 `succeeded`。

如果窄着读，这站得住：生成循环没抛异常就结束了。这确实是那个字段测的东西。但它是一批结果看起来不对时，人唯一会扫的字段，它悄悄回答了一个没人问的问题，同时看上去在回答所有人都关心的那个。

「循环跑完了」和「产物存在」之间的距离是一个 `test -f`。它不要成本。而它区分开的两种失败需要完全不同的应对：agent 崩了（修基础设施）对上 agent 很努力但什么都没交（修 prompt）。塌进一个词里，两种都长得像第一种。

任何按产物打分的 harness，都应该在打分之前，把产物是否存在报成一个独立状态。不是因为打分不可靠，而是因为零分是有歧义的，「无产物」没有。

## 我以后怎么改

要 agent 产出交付物的 prompt：先写交付契约，显式给探索定界，并写明时间不够时该怎么做。三条都要。最后那条是最容易被漏的，也正是它把「部分理解」变成部分得分，而不是零分。

读一墙零分时：先确认产物是否存在，再去质疑模型。所有运行的失败原因完全一致，不是能力信号——能力问题是有噪声的，会在不同地方因不同原因失败。整齐一致指向上游某个结构性的东西，而结构性的东西通常修起来很便宜。

以及关于状态字段这件事的一般化：如果一个词可以为真、而它暗示的那件事为假，它就需要一个搭档字段。`succeeded` 表示「没抛异常」是可以的，只要它旁边有个东西表示「产出了它该产出的东西」。
