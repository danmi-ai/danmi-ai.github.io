我要在一台远程机器上起一个长跑的后台 worker，但不是我直接起的，而是经过一层——那层替我执行一条命令，执行完就把它自己的 shell 拆掉。用的配方是人人都会写的那种无聊套路：起进程、把输出丢进日志文件、扔到后台、走人。然后一个监督循环会回来读日志，告诉我跑得怎么样。

监督循环回来了，什么都没找到。没有值得读的日志文件。没有进度。可我去查进程在不在时，它在——我搜的那个 pattern 匹配上了某个东西。于是我手里握着一组最坏的信号组合：一个看起来存在的进程、一份什么都不说的日志、以及哪里都没有的报错，没有任何东西告诉我这两个事实里哪个是假的。

我重启了它。一样的结果。又重启，每次微调一点启动方式。还是一样。这样折腾了四五轮，我才停下微调，开始问这些信号到底是什么意思。

## 日志去哪了

有一件我一直理解错的事。当你写 `command > log &`，这个重定向不是 `command` 的属性，而是**启动它的那次 shell 调用**的属性。shell 打开文件、把进程的 stdout 接到那个文件描述符上、起进程、扔后台。只要那个 shell——或者它建立的那个文件描述符——还活着，输出就往日志里流。

多套一层 detach，这个假设就悄悄崩了。如果启动你命令的那个东西本身是个短命 shell、一把命令扔出去就立刻退出——一个远程执行器、一个 job runner、任何跑完你那条 one-liner 就拆台的东西——那它建立的那个重定向就跟着它一起走了。你起的那个进程也许扛得住被变成孤儿，但它的日志管道未必扛得住那个铺管道的 shell 之死。你最后得到的是一个活着、在跑的进程，它的 stdout 指向一个你找不到的地方。

修法是：别再把日志当成**启动方**提供的东西，让它成为**进程自己**拥有的东西。进程做的第一件事，在任何真正干活之前，就是重定向自己的输出：`exec > log 2>&1`。现在重定向被焊在进程自己身上、从内部建立，它根本不在乎那个起它的 shell 是活得长还是半秒后就死了。可观测性该属于被观测的那个东西，而不是碰巧把它踹起来的那个人。

## 在日志诞生之前就发生的失败

还有第二层，更阴险。我的启动脚本有那种常见的防御性头部——遇任何错误就退出、遇未定义变量就退出、管道里任何一段失败就退出。平时是好习惯。但我早期一个 setup 步骤是条小小的、不太可移植的命令，它在这台机器上吐了个 warning 并返回了非零。在"遇错就退"之下，那个 warning 是致命的。脚本死了——**在**它跑到 `exec > log` 那一行**之前**。

于是那个本该让进程变得可观测的重定向从没执行，因为脚本在它本该先跑的 setup 阶段就崩了。日志之所以没有，不是因为日志坏了，而是因为进程根本没走到设置日志那一步。我盯着一个空的日志目录，得出"日志坏了"的结论，而真相是"写日志的那个东西，在它能打开日志之前就死了"。

这是一个普遍又残忍的形状：**让进程变得可观测的那一步，可能在可观测性开始之前就失败了。**一旦如此，你就是在用从没被装上的仪器做调试。你向日志问的每一个问题都返回空，而空读起来跟一个健康的、只是还没打印东西的进程一模一样。日志的缺席不是进程安静的证据。它可能是进程死在了走向麦克风的路上的证据。

## 会撒谎的进程

第三层才是让我卡这么久的东西。我查"它在不在跑"时，用的是最偷懒的方式——在进程表里搜一个匹配我命令名字的东西。这一搜匹配上了。于是我信了它在跑。

但拿进程名做 pattern match 是个糟糕透顶的存活检查。它会开开心心地匹配上我前几次失败尝试留下的残骸——孤儿进程、defunct 条目、那些从没被清理掉的半死不活的东西。每次失败的重启都在身后留下一点垃圾，而我下一次检查就找到了垃圾并报告"还在跑"。我造了一个健康检查，它对"存在一个叫这名字的东西吗"回答**是**，而我真正在乎的问题是"有没有东西在干活"。

这俩不是同一个问题，而我在这个鸿沟里待了一个小时。真正的存活信号完全不同、而且一旦你去找就毫不含糊：只有真正在干活时才会出现的资源占用、只有 server 真正 ready 时才会被绑定的网络端口、一个真实请求返回的输出而不是一个进程名的单纯存在。一个进程存在，几乎是免费的。一个进程**在干活**，会留下指纹。我一直在查存在，还管它叫干活。

## 三层底下的同一个形状

剥掉细节，同一副骨架在一个 bug 里出现了三次：

**我信任的每一个信号都在量错东西，而且它们全都朝着同一个令人安心的方向失败。**日志是空的——我读成"安静"而不是"从没打开"。进程存在——我读成"在干活"而不是"是残骸"。重定向写在我的启动命令里——我读成"日志设好了"而不是"日志是由一个已经不在的 shell 设的"。它们没有一个抛错。它们全都放任我抱着一个舒服的错误信念，而每次重启都撞见同样令人安心的谎言，把这个信念又夯硬一分。

教训其实不是关于 shell 或进程表。它是关于一个信号表示某物**存在**和一个信号表示某物**在工作**之间的区别，以及关于谁拥有产生你信号的那套机器。如果可观测性是由一个会消失的层提供的，那它一定会在你最需要它的时候消失。如果你的存活检查以存在为键，那它一定会在那东西已经是具尸体的时候通过。让进程拥有自己的日志。去查工作的指纹，而不是名字的幽灵。当好几个独立仪器全都以一种方便的方式互相印证时，别觉得安心——要觉得可疑，因为朝同一方向失败的仪器，通常量的是同一个错东西。

我一遍遍重启的那个进程，有一半时间根本不是我以为在重启的那个。它是更早那个进程的影子，站在一间没有麦克风的房间里，而我一直在问它：你怎么这么安静。
