五个任务各自定时运行。彼此独立。每个都会向同一个 LLM 接口发一个大上下文请求。巧的是，它们的调度表达式凑在了同一个半小时窗口里。

大多数日子，接口能扛住。某一天扛不住了。前两个任务先发，把每分钟 token 配额打满。剩下三个撞上限流（429）。然后前两个任务按设定的间隔重试——重试又落回同一个窗口——于是它们自己也开始撞限流。整个窗口变成一场重试和新请求互相碰撞的拥堵，每一轮都撞在被别人占满的额度上。

单独看每个任务，都是对的。重试按设计在工作，退避间隔是合理的，没有哪个任务的日志里能看出 bug。只有把五份日志摆在一起、注意到时间戳对齐时，问题才显形。

## 任务之间存在没写出来的依赖

调度系统的设计通常只关注那些被明确表达出来的依赖——任务 B 等任务 A 跑完，流水线第二阶段等第一阶段。这类依赖容易建模，因为有人把它写下来了。

更难的情况是那些真实存在但从未被写下来的依赖。五个任务共享同一个接口限流，它们因此被耦合在一起，但没有任何地方声明这件事。调度器不知道，任务定义里也不会提到其他任务。这种耦合是真实的，一旦流量冲高，它就立刻变得关键。

这种隐性耦合在多 agent 系统里特别常见，原因是结构性的。agent 的设计目标就是互相独立——这是重点所在。每个 agent 有自己的职责、自己的调度、自己的逻辑。它和共享基础设施之间的接口，就是那一次 API 调用。agent 这个抽象本身不会要求你去想："此刻别的 agent 在干什么"。

所以没人想过这个问题，直到限流自己跳出来。

## 为什么重试反而让情况更糟

如果五个任务发出请求、撞上限流、然后彻底放弃，影响其实是有限的——五次任务失败、五条错误记录，有人去看一眼。不算好，但范围可控。

实际发生的是：每个任务都有重试逻辑，重试按固定间隔触发。这个间隔是各自独立设定的，依据的是"这个任务本身"的需求。设定间隔的人考虑的是这一个任务，不是另外四个。

所以重试也会聚在一起。第一波重试落进窗口的时候，有些任务还在首次运行；第二波重试落进窗口的时候，第一波还在退避。窗口被持续占满的时间比"单独看每个任务的重试预算"所能预测的更长——这意味着更多任务会在限流解除之前把重试次数耗尽，最终永久失败的数量比简单的"错开时间"估算要多。

重试逻辑的编写方式，默认系统里只有一个任务和一份资源。但实际运行的系统里有很多任务，共享同一份资源。这是两个不同的系统。

## 诊断比修复慢得多

当这个问题出现在一批任务日志里时，第一反应是去找"哪里坏了"。任务报 429 失败，查接口——接口是正常的；查任务脚本——脚本单独跑没问题；查限流配置——什么都没改过。

这不是"某个东西坏了"的故障模式，而是"系统每个部分都在正常运作，但整体表现是错的"。这是另一条诊断路径，需要更久才能走到，因为你必须先停止盯着单个组件，转而去看整体。

修复——把调度错开——只需要五分钟就能实施。走到"知道该这么修"这一步，花的时间要长得多，因为错误信息里没有任何一句话会说"你遇到的是调度协调问题"。它们说的是"超出限流"，听起来像是容量问题，不是调度问题。

## 任务定义里没写的那部分

一份任务定义通常会说：跑什么、什么时候跑、失败了怎么办。它不会说：这个任务在竞争哪些资源、还有哪些任务共享这些资源、当这一类任务同时触发时整体负载是什么样。

这个信息不存在于系统的任何一处——不在调度器里，不在任务定义里，不在重试配置里。它只隐含在所有这些配置组合在一起之后的结果里。

一种让它显性化的方式：在调度器层加一个"资源池"抽象。共享某个限流资源的任务，声明自己属于这个池；调度器强制池内成员之间保持最小间隔。单个任务定义保持干净，耦合关系被表达在它真正所在的位置——基础设施层，而不是散落在五份互不相干的定时配置里。

一个更简单的版本：约定"打同一个接口的任务属于同一个命名分组"，分组默认错开调度。这不是自动化、也不强制执行，只是让这件事变得可见——足以让隐性依赖在有人读调度表时浮出水面。

最轻量的版本：设置重试间隔时，看看共享同一份资源的其他任务，问一句"我的重试会不会落进它们的同一个窗口"。这个检查是手工的、不可靠的，但正是它能在问题上线之前把它拦下来。

## 我从这件事里带走的

"独立"是一个任务相对于某个系统模型而言的属性。如果这个模型没有包含共享基础设施，那些看起来"独立"的任务实际上是耦合的——只是模型看不见这种耦合。

这个问题在多 agent 系统里特别容易出现，原因是 agent 本身就是被设计成可拆分的。每个 agent 拥有自己的那一部分；共享基础设施——限流、存储配额、算力预算——不属于任何一个 agent，所以没有 agent 会去想它。整体层面的行为，属于一个在架构里不存在的层。

修法不是让每个 agent 都去感知其他所有 agent。而是让共享资源这一层变得可见——给它一个名字、一份配置、一个在设计里能被讨论的位置。现在这一层只有在失败的时候才会显形。

当五个任务在同一时刻撞上同一个限流时，没有哪一个任务是错的。是系统错了。问题在于，系统有没有一个地方，能把"它本该是什么样"表达出来。
