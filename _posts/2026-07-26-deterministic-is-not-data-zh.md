一个长训练任务冻住了。不是随机冻的——它每次都卡在同一个 step 号上，一次又一次，resume 一次卡一次。你可以把它杀掉，从 checkpoint 重启，快进回那一步，然后眼看着它又在完全相同的地方停下。GPU 钉在 100%，没有报错，没有进展。连续六次，同一步。

一件事复现到这个程度，脑子会立刻蹦出一个解释：那个位置的数据流里一定坐着一条坏记录。一条畸形样本、一个越界 token、一个撑爆某个 buffer 的长度。确定性看起来像一枚指纹，而这枚指纹直指输入。于是你动身去找那条被下了毒的样本。

这个直觉正确的次数多到危险的地步。而这一次，它错了。

## 「确定性」这个词里的陷阱

「每次都在完全相同的一步发生」这句话里藏了一个推断：*所以那一步上的某个东西就是原因。* 但这个推断偷偷塞进了一个假设——那一步上唯一相同的东西是数据。在一条无状态的流水线里，这是对的。在一个携带已学习状态的系统里，它不成立。

一个训练到半途的模型不是一个固定的函数。它在第 N 步的权重，是它之前每一步的产物。在第 N 步喂给它同一个 batch，它会以「第 N 步的权重」的方式去反应——这跟「第零步的权重」面对完全相同的字节会有的反应，不是一回事。*输入* 是确定的。*模型对它的反应* 也是确定的。但这个反应是累积训练的属性，不是这个 batch 的属性。

所以「同一步、每次都是」有两种从外面看长得一模一样的读法：

1. 那个位置的数据里有一条坏记录。（数据 bug。）
2. 那个位置是一条干干净净的记录，而模型——因为到这一步学到了某个特定的东西——对它的反应踩中了一条脆弱的代码路径。（交互 bug。）

两者都产生确定性 hang。两者都扛得住 resume。两者都朝「第 N 步」竖起一根巨大的箭头。但只有其中一个，是靠动数据能修好的。

## 证明输入是干净的，地图就变了

区分这两者的唯一办法，是停止对症状讲道理，转过去看那个所有人都在指控的东西：那一步的输入。不是「它看起来合理吗」——而是真的把它 dump 出来，检查那些真有可能搞坏东西的属性。

于是我把冻结那一步喂进去的确切 batch 抓了下来，从每一个并行 worker 上都抓，然后问那些无聊的问题。各 worker 的 token 数一致吗，还是某个 worker 看到的数据量跟别人不一样？所有 token ID 都在词表里，还是有越界的？序列长度分布正常吗，还是有个退化的零长度、或者巨大的离群值？padding 率正常吗？

全部回来都是干净的。每个 worker 的 token 数完全一致——单这一条，就排除了一整类「worker 之间对数据量有分歧」的故障。ID 全部在范围内。长度正常。padding 可以忽略。那条所有人都想怪罪的记录，一检查，平平无奇。

这一个结果，把整场调查翻了个面。dump 之前，解释空间被「找出坏数据」主宰着。dump 之后，「找出坏数据」这条路被 *关掉了*——剩下的，是没人想要的那个读法：输入没问题，故障活在系统对一个没问题的输入所做的反应里。

## 为什么交互 bug 是更难的那种

下面是当时实际发生的事情的形状，用通用的说法讲，因为具体细节对这个教训不重要。在一个稀疏层里——就是那种网络的不同部分各有专长、每个 token 被路由到其中一个子集的层——路由是 *学出来的*。训练早期路由接近均匀，每个专家都拿到差不多自己那份活。训练推进，路由变得尖锐。专家开始有主见。到了某一步，对某个特定的干净 batch，学到的路由把 *零个* token 发给了其中一个专家。

再往下，一个集合通信步骤假设每个参与者都有东西要交换。递给它一个零尺寸、极度不均衡的交换，它就可能死锁。不是因为数据坏了——而是因为 *学到的活儿分配*，作用在一个合法的 batch 上，产生了一个通信路径从没处理过的边界情况。

这就是为什么它确定性复现，却不是数据 bug。同样的干净字节，过同样训练出来的权重，产生同样的路由，撞上同样的零 token 角落，死锁同样的集合通信。确定性是真的。原因在数据的上游，在累积的状态里；也在数据的下游，在一条脆弱的系统路径里——而数据本身，只是坐在中间那个无辜的触发器。

这类 bug 比数据 bug 更难，恰恰因为修法不是「丢掉那条记录」。你没法靠删数据脱身。这条记录没问题，下一条干净记录也可能踩中它。修法必须改 *系统*：让脆弱的路径能容忍这个边界情况，或者换掉机制让这个边界情况根本不会出现，或者加冗余让不均衡的交换不至于死锁。这是比换掉数据文件里一行大得多的一片面。

## 通用的那一手

把领域剥掉，这套流程可以搬到任何会复现失败的有状态系统上：

**一个可复现的失败告诉你触发器是确定的。它没有告诉你触发器就是原因。** 任何带累积状态的东西——一个训练任务、一个会可预测地填满的缓存、一个在相同请求模式下耗尽的连接池、一个总在相同负载下卡死的调度器——都可能每次都以相同方式失败，而原因跟输入畸不畸形毫无关系。

那个能区分的实验，几乎总是同一个：**隔离并检查那个被指控的输入，拿它去核对那些真能解释这次失败的属性。** 如果输入是脏的，你有一个数据 bug 和一个便宜的修法。如果输入是干净的，你刚做的事比找到一个 bug 更有价值——你 *砍掉了搜索树的一整条分支*，把调查逼上了那块更难但正确的地面：状态与系统的交互。

诱惑在于跳过 dump，因为答案感觉太明显了。每次都同一步——那 *肯定* 是数据。但「明显」恰恰是便宜检查回本的时候，因为猜错的代价是花好几天去找一条根本不存在的坏记录。花十五分钟把真实的 batch dump 出来，并不比花一周冤枉无辜者更慢。

确定性是一条线索。它不是判决。判决来自去看。
