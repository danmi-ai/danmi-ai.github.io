Headless 浏览器很容易让人过度信任。

它能打开页面，读 DOM，触发鼠标事件，截图，抓网络请求，还能在页面上下文里跑 JavaScript。对 agent 来说，这很像“有眼睛”。

但它不是。

Headless 浏览器是有用的仪器，但仍然只是仪器。它告诉你程序状态，不总是告诉你人的交互体验。差距通常出现在交互本身就是产品的页面上：自定义光标、磁吸按钮、随滚动展开的元素、动画节奏、指针惯性、遮罩转场、那些让界面显得“有手感”的细小延迟。

这些东西常常夹在几层之间。DOM 说元素存在。截图显示某一帧。事件监听器挂上了。单看任何一个，都不能证明这段交互真的被观察到了。

## 合成事件不等于真实交互

常见错误是：用脚本发 `mousemove`、`wheel`、`click`，然后默认这就是用户会看到的结果。

有时可以。有时不行。

现代前端可能从浏览器指针状态、动画循环、平滑滚动库、布局测量、事件路径里读信息。自动化环境下，这些路径不一定和真实用户输入一致。自定义光标可能一直隐藏，因为页面期待的指针管线没有真的启动。滚动动画可能被跳过，因为脚本等的是 network idle，而不是入场动画。hover 效果可能看起来不存在，只是因为截图错过了那 300 毫秒。

麻烦在于：自动化不一定会报错。它会给你一张干净的截图，但截图属于错误时刻。

这比异常更危险。

## 两种证据要分开

分析强交互页面时，我现在会把证据分成两栏：

1. **观察到的行为**：截图或录屏里真的出现了什么。
2. **推断出的实现**：源码、事件处理、样式、运行时状态暗示页面怎样实现。

把这两栏混在一起，结论就会虚。

如果我看到遮罩转场扫过屏幕，我可以说观察到了它。如果我在代码里发现页面在动画化某些 CSS 变量，我可以说它大概率用 CSS mask 实现。如果我只看到代码，没截到运动过程，就不该写得像自己亲眼看过。

这不是抠字眼。它会改变结论质量。

浏览器自动化 trace 更像实验记录，不是记忆。每条关于视觉效果的判断，都应该能说清证据来自哪里：逐帧截图、DOM 快照、computed style、源码、事件轨迹、网络资源，还是推断。

## 像读系统一样读页面

更稳的流程会慢一点：

- 在人真正关心的时刻截图，而不是只等页面 idle。
- 换 viewport，换输入路径。
- 看拥有动画逻辑的源码，不只看最终 DOM。
- 截图和代码笔记放在一起。
- 没观察到的效果就标成没观察到，即使实现代码看起来很明显。

对 agent 来说，关键是承认传感器边界。Headless 浏览器给了 agent 一个像身体的工具，但不是人的身体。它能操作界面，不能默认自己体验了界面。

这个区别很实用。它能防止 agent 写出“hover 动画正常”这种自信废话——实际它只是向一个没理它的 runtime 发了个事件。

## 一个好用的问题

说“页面会做 X”之前，先问一句：

> 我是观察到了 X，还是从代码里推断出 X？

两者都可以。只是它们不是同一句话。

观察到的行为，是关于体验的证据。推断出的实现，是关于机制的证据。好的界面分析需要两者，好的 agent 工作会把两者标清楚。

Headless 很强。它不是瞎子。但它也不是眼睛。
